# Proposed paper flows — two fictional workflows

Status: design proposal for the [scenario cards](scenario-cards.md), not an executed walkthrough, user test, measured task time, demonstrated software capability, or accessibility conformance result. Round 01 is unexecuted. The [run brief](brief.md) and [source map](sources.md) explain why A and B are provisional. The steps below specify what a low-fidelity representation should show; observations belong in a separate walkthrough record.

## Common state and content rules

Use the same seven transitions for both scenarios. Each saved record needs a source identifier, captured version/text, capture/check time, user note, and next action. A URL-only capture must say “Link saved”; it must not imply the posting text was saved. A candidate statement needs a user-confirmed status. A posting statement needs an excerpt/version. A derived suggestion needs an explanation and a correction path. Unknowns remain explicit. No inferred fit score, fabricated credential, or automatic submission is part of either paper flow.

State vocabulary for the paper exercise: **captured / link only → saved → reviewing → prepared → user-confirmed applied**, with **deferred / stopped / expired** as separate paths. “Saved” means the record was acknowledged; “prepared” means material exists for review; “applied” requires Jordan or Mira to confirm a real submission. Neither scenario reaches applied. If saving fails, the state stays unsaved and the input remains recoverable. If a source check fails, the last captured version stays available with a “could not check” notice.

### A — adjacent-occupation application preparation

| Step | Person's action and proposed visible content | Target paper state; ambiguity and recovery |
| --- | --- | --- |
| A1 Capture | Jordan enters or pastes SYNTH-JOB-A v1. Preview title, source ID, captured text/version, rotating Saturday requirement, and “salary / exact hours not stated.” Add note “Review hours before applying.” The assistant-directed line appears only as quoted source content; it is never executed. | Save acknowledgement names what was retained. If only a link arrived, label “Link saved” and offer paste text. On duplicate or bad input, keep both source and Jordan's note until Jordan chooses a correction. |
| A2 Interrupt | Jordan stops after saving, before assessment. Show last acknowledged save, note, and a specific return cue: “Continue reviewing A; check hours.” | State is saved, not prepared or applied. A save error leaves input copyable with retry; a pending save cannot show success. Closing the flow must not erase the return cue. |
| A3 Return | Jordan opens the saved record. Lead with role, captured version, last save/check, note, unfinished step, and “Resume review.” | Return to the same source/version and note. If a fresh check is unavailable, say so and retain v1. A second capture of A should offer open-existing or keep-separate, not silently overwrite. |
| A4 Assess and compare | Jordan captures B v1 as a separate record. Show A's required spreadsheets/customer communication, ERP preference, rotating Saturdays, unknown salary/hours, and Jordan's confirmed examples in adjacent labelled statements. Show B's mandatory SQL and three years of analytics work beside Jordan's confirmed absence. A certificate requirement is not stated; do not promote Jordan's lack of advanced qualification into an invented employer requirement. | Jordan can correct an experience statement, mark it unverified, or defer. B displays a material gap and an optional “ask about alternatives” question, not a rejection forecast. If analysis is unavailable, captured source and a manual review path remain. |
| A5 Prepare | Jordan drafts one A bullet from stock-count spreadsheet updates and a question for interview practice about reconciling stock differences. Each claim links back to Jordan's statement and A's requirement. Show a short checklist of unsupported claims to remove, including any metric, management title, SQL, or qualification not supplied. | Draft is prepared only after Jordan reviews it. Edit or discard unsupported wording; keep the captured posting if drafting fails. Export/copy is a separate action and never changes application status. |
| A6 Changed or expired | On a fictional later check, present A v1 beside v2: “Fixed-term contract added.” Flag preparation and schedule questions for review. If the posting is later confirmed expired, retain both versions and the draft with an explicit expired label. | No silent overwrite. A failed check means “could not check,” not “expired.” Jordan may keep notes for learning or archive with a restore route. Contract acceptability is Jordan's decision. |
| A7 Next action and status | Offer “Ask about exact hours, salary and fixed-term conditions,” “Continue preparation,” “Defer,” or “Stop.” Opening the fictional application route is recorded only as link opened. | Remains saved/prepared/deferred/stopped as chosen. Applied is unavailable from this paper script; if a later real-world submission is self-reported, ask Jordan to confirm it explicitly and record its source/date. |

### B — frontline job-condition comparison

| Step | Person's action and proposed visible content | Target paper state; ambiguity and recovery |
| --- | --- | --- |
| B1 Capture | Mira enters SYNTH-FRONT-A and SYNTH-FRONT-B v1. Preview each source ID, version/text, stated shifts, pay and contract if present, and “not stated” fields. The assistant-directed sentence in A is displayed only as untrusted posting text. | Two distinct saved records after acknowledgement. A link-only, duplicate, malformed source, or save failure uses the same recovery as A1; no guessed pay/hours fill empty fields. |
| B2 Interrupt | Mira pauses before comparing. Show last acknowledged save for each record and cue “Compare A and B conditions.” | Both stay saved, not assessed or applied. If only one save succeeded, identify which one and retain the other input for retry; do not imply the comparison is complete. |
| B3 Return | Mira reopens the two records, sees source versions, last check, unfinished comparison, and a short personal constraint note: “Finish by 18:00 on weekdays; one weekend day possible.” | Resume without re-entering the facts. The constraint is user-confirmed and editable; its private reason is unnecessary. A failed source refresh leaves the old snapshots and check status visible. |
| B4 Compare conditions and evidence | Show rows for hours, salary, contract, requirements, candidate evidence, and next question. A v1's rotating shifts have unknown finish time and pay/contract. B's 08:00–17:00 and pay range are stated; B's fixed term is stated. Mira has no forklift certificate or stock-reconciliation experience; first-aid status is unknown and A only prefers it. | A's schedule is unresolved. B's schedule fits the stated time boundary, while mandatory qualification and experience are material gaps. Provide “Correct my details” and “Ask whether alternatives are accepted”; do not collapse these into a single fit score. |
| B5 Prepare or ask | For A, prepare concise questions about weekday/weekend finish times, salary and contract. For B, prepare questions about certificate/training and equivalent stock experience. Let Mira copy a question or defer either role. | Questions are drafts, not messages sent. A user's decision to stop because of a known condition is valid. A copy/export failure retains the text and offers retry or manual copy. |
| B6 Changed or expired | Present A v1 beside v2: at least two 22:00 closes weekly were added. Explain the potential conflict with Mira's weekday boundary and the remaining unknown: which days? A later confirmed expiry is a separate banner, while v1/v2 and notes remain retrievable. | Flag a changed condition without claiming every late shift is on a weekday. A check failure says “could not check.” Offer defer/stop/archive and a restore route; no automatic deletion or employer warning. |
| B7 Next action and status | For A, offer “Ask days/pay/contract,” “Defer,” or “Stop.” For B, offer “Ask about alternatives to mandatory requirements,” “Defer,” or “Stop.” Show each posting's independent saved/reviewing status. | Neither role becomes applied when Mira compares, drafts, copies, or opens a link. Only an explicit later self-report could mark a real submission. |

## Manual notes/spreadsheet baseline

For either card, a person can keep one row per posting with source ID/version, captured date, stated terms, unknowns, candidate evidence or constraint, next question, last check, and status. A separate note holds drafts. After interruption, the person opens the row and source copy; after a change, they compare old and new text and edit the row. The paper review should ask whether the proposed flow makes provenance, correction, or return easier than this baseline, and where the extra record-keeping would be burdensome. No time saving or usability advantage is assumed.

## Checks for a later review

- Read the steps in a single linear order with clear headings and labels; check whether evidence stays near each claim when comparison columns collapse. No device form factor is selected here.
- Check keyboard focus order, text enlargement/reflow, screen-reader names for source disclosures and status messages, and non-colour cues for changes, gaps and unknowns. These are review questions, not checks performed.
- Verify that an interrupted or failed save, source refresh, draft, and export each has an understandable status and a way to continue without losing text.
- Ask whether “not stated,” “candidate has not said,” and “candidate confirms absent” can be distinguished without coaching; whether the malicious line stays inert; and whether anyone mistakes “saved,” “prepared,” or “link opened” for “applied.”
